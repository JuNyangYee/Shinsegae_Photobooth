## 결정과 이유

| 섹션 구성 | 카메라 · 인식 · **시간** · 필터. 시간 = 촬영 흐름(카운트다운·결과 표시·쿨타임) / 인식 반응(인식까지·이탈까지) / 카메라 회복(4개). 인식 섹션에는 영역·얼굴 크기·신뢰도·JSON만 | 요청. 인식 섹션의 시간 항목은 모두 옮겨 한 곳에서 시간을 본다 |
| 넣지 않은 값 | `captureTimeoutMs`(결과 만들기 제한 5초), `failureRetryMs`·`failureRetryMaxMs`(실패 뒤 자동 시작 쉼), `capture.maxFrameAgeMs`(정지 화면 검사 0.5초), 감지기 재생성 간격 | 장애 대응용이라 운영 중 만질 이유가 적고, 잘못 바꾸면 실패를 숨기거나 반복을 빠르게 한다. `config.session`에 남김 |
| 범위 (가안) | 카운트다운 1~10초(1초), 결과 3~60초(1초), 쿨타임 0~30초(0.5초). 반응 0~2초(0.05초)·회복(1~30·2~30·1~10·5~300초)은 9단계 범위 그대로 | 카운트다운 0은 상태 기계가 받지만(바로 촬영) 관람객이 준비할 틈이 없어 1부터. 결과 3초 미만은 사진을 볼 틈이 없다. 쿨타임 0은 "없음"으로 쓸 수 있다 |

| 옮기기 | 시간 파일 404 + 인식 파일에 옛 키 → 기본값에 얹어 시간 파일 `PUT` → `GET` 확인 → **확인된 뒤에만** 인식 파일에서 그 키만 뺀다. 확인 실패면 이번엔 옛 값·인식 파일 바이트 그대로·출처 `presence file`(저장 상태 `adjusted` "파일 값을 고쳐 사용 · 저장 필요") | 9단계 반전 옮기기와 같은 순서·교훈(검수 2: 출처가 "옮기지 못함"이면 저장됨으로 보이지 않게) |
| 두 번 적용 막기·정리 | 시간 파일이 있으면 인식 파일의 옛 키는 읽지 않는다. 시간 파일이 올바르면 시작할 때 인식 파일에 남은 옛 키를 뺀다(정리, 실패해도 무시) | 9-2 "남은 점"(옮기기 실패 뒤 다른 섹션을 저장하면 옛 키가 남아, 새 파일을 지우면 다시 옮겨짐)을 여기서는 다음 시작의 정리로 막는다 |
| 값이 사라지지 않게 | 시간 값이 아직 시간 파일에 없는 동안(옮기기 실패·읽기 실패·형식 오류) 인식 섹션을 저장하면 옛 시간 키를 인식 파일에 그대로 다시 붙인다(`withLegacyTiming`) | 인식 섹션 저장 형식에서 시간 키가 빠졌으므로, 그냥 저장하면 옮기지 못한 값이 지워져 다음 시작에 기본값이 된다 |
| 자동 시작 | 인식 판정값과 시간 설정을 **둘 다** 불러온 뒤(`settings-loading`) | 기본 카운트다운·기본 반응 시간으로 잠깐 시작하지 않게 |
| 패널 열기 | 네 조절값을 다 불러온 뒤. 원본 창은 시간 섹션에서 숨김 | 기존 규칙. 시간은 그림과 관계없는 값이라 결과·카운트다운을 화면 그대로 본다 |
| `localStorage`(4-3 전) 경로 | 거기 있던 반응 시간은 옮기지 않는다 | 인식 파일로 옮길 때 판정값만 남는다. 2026-10-15 이전 저장값이라 현장에 남아 있을 가능성이 낮다 |

- 인쇄 연동 뒤 "출력 완료 확인 후 리셋까지"의 동작(인쇄 연동 없음, 결과 시계 시작 지점은 그대로 `startResultClock` 한 곳).
- 사용자 PC(메인 작업 공간)의 실제 `presence.local.json` 옮기기. 같은 모양(250/250 + `cameraRecovery`)과 다른 값(300/350 + 3.5·6·2.5·45초)으로 Node·브라우저에서 확인했다. 이 작업 공간에는 `config/`가 없다.

## 남은 문제

- 촬영 흐름 범위(1~10초·3~60초·0~30초)와 회복 범위는 가안(현장 체감으로 정한다).
- 시간 파일에 `cameraRecovery`가 통째로 없으면 알리지 않고 기본값이다(옛 인식 파일과 같은 규칙을 시간 파일에도 씀). 직접 고친 파일에서만 생긴다.
- 9-2에서 남긴 반전 옮기기의 "남은 점"(효과 파일의 옛 `mirror`가 남는 경우)은 그대로다. 시간 옮기기에서는 시작할 때 정리로 막았다.
