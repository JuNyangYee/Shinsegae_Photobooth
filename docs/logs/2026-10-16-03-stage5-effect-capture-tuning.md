## 결정과 이유

### 촬영 결과에 효과

- **같은 프레임·그림 번호·seed:** 미리보기가 그릴 때마다 `lastDrawing`(tick·seed·설정·보이는 영역)을 기억한다. 그 그림의 카메라 프레임은 렌더러의 소스 텍스처에 남아 있다.
  - 결과는 이 텍스처를 다시 올리지 않고(`render(null, …)`) 같은 seed·설정으로 결과 크기에 그린다. 화면에 보이던 그림의 프레임 그대로다.
  - 그 사이에 바뀌지 않는다. `capture.js`가 프레임을 잡은 같은 작업의 마이크로태스크에서 효과 단계를 부르고, 효과 단계는 끝까지 동기다. 미리보기는 `requestAnimationFrame`에서만 새 프레임을 올린다.
  - `capture.js`의 원본 프레임 잡기(동기, 새 프레임 500ms 확인)는 그대로 둔다. 원본 사진은 실패 시 대신할 사진으로만 쓴다. 이 원본은 셔터 순간의 최신 카메라 프레임이라, 효과 사진보다 1/fps 이내로 새 프레임일 수 있다.
- **화면 밖 렌더:** 미리보기 처리 해상도가 1이 아니어도 결과는 따로 1080 기준으로 그린다. 렌더러가 해상도별 텍스처 묶음을 따로 두므로 미리보기 묶음·캔버스를 덮지 않는다. 1이면 같은 묶음을 쓴다.
- **화소 읽기는 동기 `readPixels`.** 측정상 14.7~18.3ms이고 촬영 순간 한 번뿐이라 비동기 읽기(PBO·fence)는 넣지 않았다. 아래 성능 참고.
- **효과 실패 → 원본 사진(지시대로).** 촬영 실패로 처리하지 않는 쪽이 맞다고 판단했다.
  - 관람객은 이미 3·2·1을 거쳐 찍혔고 비접촉이라 다시 찍을 방법이 없다. 촬영 실패면 사진 없이 대기로 돌아간다.
  - 효과 장애는 대부분 미리보기에서 이미 원본으로 보이던 경우다(장애·컨텍스트 손실).
  - 원본 사진도 결과 크기로 줄여 결과 사진 크기를 일정하게 둔다. D `photo-fx` 줄과 경고 로그(`effect-capture` 분류, 반복은 요약)에 남긴다.
- **`config.effect.enabled` false면** 결과도 예전처럼 원본 해상도 그대로다(효과를 끈 설정의 뜻을 바꾸지 않음).

### 조절 화면 `E`

- 키 `E`는 `D`·`R`·`S`·`X`·`P`·`Esc`와 겹치지 않는다.
- 값 7개는 원본 갤러리 UI에 있는 것(강도·붓 크기·획 다시 그리기·초당 그림·색 보정)과 지시의 보완 층 오차 문턱·미리보기 처리 해상도다. 범위는 원본 슬라이더와 같다.
  - 원본 UI의 "비교 위치"·"처리 해상도(q)"는 넣지 않았다. 비교 위치는 `oil2f`에 없는 비교 기능이고, q는 `oil2f`에 영향이 없다(로그 02).
- 저장·취소·기본값·저장하지 않고 닫으면 되돌리기·저장 중 닫기는 `presence-tuning.js`와 같은 구조로 만들었다(Node 테스트 6개).
- **열려 있는 동안 자동 촬영을 막는다(`R`과 같은 규칙).** 효과는 판정에 영향이 없지만, 운영자가 화면 앞에 서서 자기 모습에 입혀진 효과를 보며 맞춘다. 그때 자동 회차가 시작되면 카운트다운·결과 사진이 미리보기를 가린다. 결과를 확인하려면 `S`를 쓴다.
- **`R`과 `E`는 한 번에 하나만 연다.** 한쪽이 열려 있으면 다른 키를 무시한다. 열면서 다른 쪽을 닫으면 저장하지 않은 변경이 말없이 취소되기 때문이다.

### 파일 저장

- `serve.ps1`의 조절값 API를 **고정 경로 표**(서수 비교 `Dictionary`: URL → 파일 이름)로 바꾸고 `/local-api/effect-settings` → `config/effect.local.json`을 더했다.
  - 두 경로가 같은 쓰기 검사(CSRF 방어)·16KB 상한·JSON 객체 검사·원자적 쓰기·재시도 함수를 쓴다. 임시 파일 이름은 `<파일 이름>.<guid>.tmp`다.
  - `.gitignore`의 `/config/*.local.json`·`/config/*.tmp`가 이미 덮는다.
- **불러오기 순서: 파일 → 기본값(지시대로).** `localStorage`에서 옮길 예전 값이 없다.
  - 불러오기가 끝나기 전에는 기본값으로 그리고, 끝나면 반영한다. 자동 촬영을 막지 않는다. 효과는 판정과 무관하고, 시작 직후 최대 3초 동안 찍혀도 미리보기와 결과는 같은 값이다.
- 저장 형식에는 조절값 7개만 넣는다. 붓 층 모양은 운영자가 바꾸지 않으므로 `config.effect` 기본값을 쓴다. 나중에 기본 층을 바꿔도 저장 파일이 덮어쓰지 않는다.

### 확인 도구

- `S` 사이클이 든 시나리오는 `withAutoPaused`로 감쌌다. `P`를 켜고, 그 전에 시작된 자동 회차가 끝나 대기가 될 때까지 기다린 뒤 돌리고, 끝나면 되돌린다. 장시간 실측(`--soak`)은 바꾸지 않았다.

### 서버 API (실제 HTTP, 저장소 밖 임시 스크립트)

`serve.ps1`을 남는 포트로 띄우고, 헤더를 그대로 보내도록 `node:http`로 두 경로에 같은 묶음을 보냈다(경로마다 32건 + 공통 7건). **69/71 통과.**

- 통과
  - `GET` 404(파일 없음) → `PUT` 204 → 파일 바이트 = 본문 → `GET` 200 같은 바이트·`application/json`
  - `charset=utf-8` 204, `Origin`·`Sec-Fetch-Site` 없는 같은 PC 요청 204
  - 거절: `X-Photobooth` 없음 403, 다른 `Origin`·다른 포트 `Origin` 403, `Sec-Fetch-Site: cross-site` 403, `Host 127.0.0.1` 400(http.sys가 먼저 거절)
  - 거절: `text/plain`·형식 없음·`charset=latin1` 415, 16385바이트 413(16384바이트는 204), 잘못된 JSON·배열·잘못된 UTF-8 400. 거절 뒤 파일 그대로
  - `POST`·`DELETE`·`PATCH`·`HEAD` 405 `Allow: GET, PUT`. 다른 출처 preflight(`OPTIONS` + `Access-Control-Request-*`) 405, CORS 헤더 없음
  - 변형 경로(대문자, 끝 `/`, 쿼리, 퍼센트 인코딩, `.json`, `/../`)·다른 `/local-api` 이름·`/local-api/` 404 또는 400
  - 두 경로에 동시 `PUT` 20건 모두 204, 끝난 뒤 각 파일이 보낸 본문 중 하나와 같음, 임시 파일 0, 정적 파일 그대로 제공
- **실패 2건 (판정 기준 문제):** 시험 스크립트가 `OPTIONS`에 `Content-Type: application/json`과 `Content-Length: 0`을 붙여 보냈다. http.sys가 스크립트보다 먼저 HTML 오류 페이지 400으로 답했다(본문이 http.sys 오류 페이지라 `serve.ps1`의 응답이 아니다). 브라우저가 실제로 보내는 preflight 형태는 위처럼 405이고 CORS 헤더가 없다. 5-2에서 바꾼 경로 판정보다 앞 단계라 이번 변경과 무관하다고 판단한다. 5-1 이전 코드로 같은 요청을 보내 보지는 않았다.

### 수정 내용 (`065a490`)

- **1 GL 오류·컨텍스트 손실:**
  - 그림을 시작하기 전에 쌓여 있던 오류를 비운다(`clearGlErrors`, 최대 16번, 손실이면 멈춤). 이전 그림·다른 코드의 오류를 이번 그림 탓으로 보지 않기 위해서다.
  - 결과 사진은 화소를 읽은 뒤, 미리보기는 출력 패스 뒤에 `checkGl`을 부른다. `isContextLost()`면 `EffectError(context-lost)`, `getError()`가 오류면 `EffectError(render-failed: GL error 0x…)`다.
  - 결과 사진 쪽 예외는 기존 경로대로 `photo-effect.js`가 원본 사진(결과 크기)으로 대신한다.
  - **미리보기에도 같은 문제가 있었다.** GL 오류가 나도 잘못된 그림을 계속 보였다. 미리보기 쪽 예외는 기존 경로대로 `effect-preview.js`가 렌더러를 버리고 원본 미리보기(`fallback`)로 간다. 손실이면 `webglcontextlost`를 기다린다.
  - 비용: `getError()`가 GPU 명령을 동기화해 미리보기 그림당 CPU 약 0.8~1ms가 더 든다. 실제 OBS 1배에서 같은 조건으로 비교했다: 검사를 뺀 상태 6.5·6.7ms(2회), 넣은 상태 7.4·7.6ms. 초당 24장에서 메인 스레드 약 2%다. rAF 60fps(25ms 넘는 간격 0)·감지 15fps·초당 24장은 같았다. 그래서 그림마다 확인한다. 느린 현장 PC에서 문제가 되면 몇 장에 한 번 확인하는 쪽을 검토한다.
- **2 프로그램 해제:** `owned`를 종류별 `Set`으로 바꾸고 등록·해제 모두 객체 자체를 쓴다. 해제는 `release(kind, object)` 한 곳이다.
- **3 생성 도중 실패:**
  - 텍스처·프레임버퍼·MRT를 만드는 즉시 `owned`에 넣는다.
  - `tex()`는 실패하면 자기 텍스처·프레임버퍼를 지운다.
  - `allocate()`는 실패하면 그 묶음에서 만든 것을 모두 지운다(`freeTargets`가 빈 칸을 건너뜀).
  - 렌더러 초기화는 실패하면 `deleteAll()`로 그때까지의 프로그램·버퍼·VAO·텍스처를 모두 지운다. 셰이더는 컴파일 실패분을 바로 지우고, 붙은 셰이더는 프로그램과 함께 지워진다.
  - `dispose()`도 `deleteAll()`을 쓴다. 테스트용으로 `liveResources()`(종류별 살아 있는 수)를 더했다.

### 회귀 테스트
