브랜치 `stage5-oil-effect`(기준 `master` `689f261`). 작업 에이전트(Opus 5.5). `paseo.json`은 건드리지 않았다.

## 사용자 결정 (2026-10-16, 오케스트레이터 전달)

- 사진 효과는 **"유화 · 획 (세부 보존)"**이다. 출처는 사용자가 지정한 필터 갤러리 `https://nau-filter-gallery.vercel.app/`의 프리셋 `oil2f`다.
- 최종 출력에 쓸 이미지를 WebGL로 실시간으로 보여 준다. 미리보기에서 이미 필터가 보이고, 촬영 결과도 같은 필터를 적용한다.
- 수치를 조절할 수 있어야 한다. 기본값은 사용자가 고른 세팅이다(강도 0.1, 붓 크기 1.25, 획 다시 그리기 0.1, 초당 24장).
- 나중에 감열지 출력용 흑백 필터를 덧씌운다. 이번에는 붙일 자리만 둔다.

- 분석하며 알게 된 점
  - 원본은 소스 크기와 관계없이 **짧은 변을 1080px로 맞춰 그린다**(`allocate`). 그래서 px 매개변수의 기준은 "짧은 변 1080px 그림"이다.

  - 붓 층의 불투명도 값(6번째)은 유화 분기에서 쓰지 않는다.
  - 원본은 정지 이미지를 한 번만 올린다. 이미지 요소를 매번 올리면 1080p에서 약 27ms가 든다(원본 주석, 하네스에서도 확인).
- **라이선스:** 페이지 본문에 라이선스·저작권 표기가 없다. 사이트의 `LICENSE`·`LICENSE.md`·`license.txt`는 404다(GET 각 1회).
  - 페이지 안의 MIT 언급은 수채 v4(MNPR, Montesdeoca 2017·2018) 출처라 `oil2f`와 관계없다.
  - 원본이 밝힌 기법 출처는 Hertzmann 1998이다.
  - `hash12`는 Dave Hoskins "Hash without Sine"(MIT)과 같은 식이다. 원본에는 표기가 없다.
  - 이식한 파일 머리말에 출처 URL·프리셋 이름·기법 출처를 남겼다.

## 결정과 이유

- **폴더:** 새 `effect/`(파일 3개)를 만들었다. 표에 `effect` → `effect`·`core`·`config`를 더했다.
  - 순수 계산은 `core/oil-paint.js`에 두었다. `test/core-deps.test.mjs`가 검사하고, 통과한다.
  - 설정 정규화는 `presence-settings.js`와 같은 "조절값의 검증·정규화" 책임이라 `config/`에 두었다.
  - `effect-preview.js`는 카메라 모듈을 부르지 않는다. `camera.isReady()`와 `<video>`를 `main.js`에서 주입받는다(`camera`·`vision`·`ui`·`effect`끼리는 서로 부르지 않는 규칙).
- **반전은 효과 입력에서 한다.** 색 보정 패스가 cover 영역을 `config.mirror`에 따라 반전해 읽고, 캔버스에는 CSS 반전을 걸지 않는다.
  - 획 방향(평평한 곳 60도 등)이 좌우 대칭이 아니어서 "효과 후 반전"은 "반전 후 효과"와 다른 그림이 된다.
  - 결과 사진도 반전된 사진에 효과를 입혀야(5-2) 미리보기와 같은 그림이 된다.
- **해상도 비례 규칙:** s = 짧은 변 / 1080. px × s, 밉 단계 + log2(s), 붓털 주기는 기준값 그대로, 법선 세기 × s, 캔버스 결 주기 × s. 표는 SYSTEM 6절에 있다.
  - 획 간격이 같이 줄어 획 수와 정규화 좌표의 획 목록이 해상도와 관계없이 같다.
  - s = 1에서는 모든 값이 원본과 같다. 그래서 원본 비교에서 화소가 같다.
- **출력 단계:** 합성 결과를 `composed` 텍스처에 그린 뒤 `FS_OUTPUT`(지금은 그대로 통과)으로 화면에 낸다. 흑백·디더링은 이 셰이더를 바꾸거나 앞에 패스를 더하면 된다. 비용은 전체 화면 패스 하나다.
- **`EXT_color_buffer_float`가 없으면 효과를 쓰지 않는다.** 원본은 RGBA8로 내려가는데, 그러면 흐름장의 음수(cos·sin)가 잘려 다른 그림이 된다. "원본과 같은 결과"를 지킬 수 없으므로 원본 미리보기로 돌아간다.
- **장애 시 재시도:** 컨텍스트 손실은 `preventDefault()` 후 `webglcontextrestored`에서 다시 만든다(GPU 프로세스 재시작 등). 생성 실패(WebGL2 없음, 셰이더 실패)는 새로고침 전까지 다시 시도하지 않는다. 같은 환경에서 다시 만들어도 실패할 가능성이 크기 때문이다.
- **관람객 안내 문구는 바꾸지 않았다.** 효과 장애에도 원본 미리보기로 촬영이 되므로 관람객이 할 일이 없다. D 화면과 콘솔 경고 1회(`errorLog`)만 둔다.
- **`preserveDrawingBuffer: false`:** tick 사이에는 다시 그리지 않아도 브라우저가 마지막으로 낸 그림을 계속 보인다(확인함: 24장/초로 그려도 화면은 60fps, 깜빡임 없음).
- **`render(null, ...)`:** 앞 소스를 다시 쓴다. 비교 하네스에서 정지 이미지를 매번 올리지 않으려고 넣었다. 5-2에서 같은 캡처 프레임을 여러 번 그릴 때도 쓸 수 있다.
- **`previewScale` 기본값은 지시의 예대로 0.5(가안)로 두었다.** 측정상 개발 PC에서는 1배도 GPU 1.2ms라 여유가 있다. 0.5배는 원본보다 부드럽게 보인다(아래 "원본과 비교"). 기본값을 1로 할지는 "질문"에 남긴다.
- **결과 표시 중에도 효과를 계속 그린다.** 결과 사진이 덮어 보이지 않지만, 멈추면 결과 → 쿨타임 전환 때 첫 그림까지 원본이 비칠 수 있다. 촬영 결과 렌더(5-2)와 GPU를 나눠 써야 하면 그때 다시 본다.

### 원본과 비교 (저장소 밖 임시 하네스, 합성 시험 이미지)

- 입력: 브라우저 캔버스로 만든 1080×1920 합성 이미지(그라데이션, 원, 줄무늬, 체크, 곡선, 글자, 작은 밝은 점, 반투명 사각형. 사람 사진 아님)를 PNG로 만들어 두 쪽에 같은 바이트로 넣었다.
  - 원본: 받은 페이지를 수정 없이 열고 페이지 전역 `loadSource`로 이미지를 넣었다. `state`를 맞춘 뒤 `renderDrawing()`, 화면 버퍼 `readPixels`.
  - 이식본: `createOilRenderer`로 같은 매개변수·seed. 비교는 RGB 채널별 절대 차이.
- 같은 GPU: RTX 5090, ANGLE D3D11, Chrome 155 headless.

| 비교 (1080×1920, s = 1) | 최대 차이 | 다른 화소 |
|---|---|---|
| 기본값 seed 0 / 1 / 500 | 0 | 0% |
| boil 0 seed 3, boil 1 seed 3 | 0 | 0% |
| 강도 1·크기 1 / 강도 1.6·크기 1.8 / 크기 0.6·색 보정 0 (seed 7) | 0 | 0% |
| boil 0·0.1·0.5·1의 seed 4 | 0 | 0% |
| 반전: 이식본(반전 uv) vs 원본(미리 반전한 PNG) | 0 | 0% |

- **기준 해상도에서는 원본과 화소가 완전히 같다.** 원인 설명이 필요한 차이가 없다.
- boil 동작(원본과 이식본 같은 값): 이웃한 그림(seed 3 → 4) 사이에 바뀌는 화소가 boil 0 → 0%, 0.1 → 29.8%(평균 차이 3.7/255), 0.5 → 81.5%, 1 → 99.7%.
- 다른 해상도 (참고: 원본 seed 0과 seed 1의 차이는 2×2 평균 기준 3.2/255, 27.7dB)

| 비교 | 평균 차이 /255 | PSNR |
|---|---|---|
| 이식본 540×960(비례 규칙) vs 원본 1080의 2×2 평균 | 10.1 | 22.3dB |
| 이식본 540×960, 비례 없이 px 그대로 vs 같은 원본 | 18.4 | 18.7dB |
| 이식본 2160×3840의 2×2 평균 vs 원본 1080 | 9.3 | 22.9dB |

- 비례 규칙으로 차이가 절반 가까이 준다. 구성(획 위치·색·방향)은 같지만 화소는 다르다.
- 남는 차이의 원인: 낮은 해상도에서 흐름장을 더 거친 이미지로 잰다. 보완 층의 오차 판정이 더 흐린 칠과 비교한다(밉 0.6 → −0.4가 0으로 잘림). 가는 획·붓털이 화소보다 작아진다.
- 합성 이미지 결과를 눈으로 봤다: 540×960은 같은 그림이 더 부드럽다(가는 선·체크 무늬 가장자리·글자 세부가 흐려짐). 확인용 PNG는 임시 폴더에만 두고 지웠다.
- 하네스 시간(그리기 + 1px `readPixels`로 GPU 완료 대기, 중앙값): 원본 1080×1920 7.6~9.8ms. 이식본 540×960 8.5ms, 1080×1920 9.3ms, 2160×3840 10.0ms. 해상도에 거의 무관하다(CPU의 획 목록이 대부분).

- **미리보기:** `OBS Virtual Camera` 1080×1920 @ 60fps. D `effect`: `running, 540x960 (preview x0.5, px scale 0.500), fps 24 -> 24 drawings/s`.

- **반전·크롭:** 효과 그림을 54×96 칸 밝기로 줄여 영상과 상관을 쟀다.

- **`S` 한 사이클:** `idle (round 1 by key, completed 1)`, 캡처 1080×1920(효과 없음, 5-2), 사진 자원 0(`taken 1, released 1`). 결과 표시 중에도 효과는 `running`이었다.
- **컨텍스트 손실:** `WEBGL_lose_context.loseContext()` → D `context-lost … -> camera preview, context lost 1x`.
  - 그동안 캔버스는 숨겨졌고, `<video>`는 재생 중, 카메라 `ready`, 감지 15fps.
  - `restoreContext()` → 다시 `running`, 캔버스 보임.
  - 콘솔 경고는 `[effect] webgl context lost -> camera preview` 1줄(의도). 그 밖에는 MediaPipe 경고 1줄(이전부터)이다.
- 외부 요청 0, 콘솔 오류 0, 페이지 예외 0.

### `npm run check:browser`

- 새 시나리오
  - "사진 효과 미리보기": 캔버스 표시·자리·CSS 반전 없음, 초당 그림 = fps ±1, 컨텍스트 손실 → 원본 미리보기 → 복구
  - "효과 WebGL2 생성 실패": 페이지 스크립트보다 먼저 효과 캔버스의 `getContext('webgl2')`만 `null` → `fallback (webgl2-unavailable…)`, 캔버스 숨김, 안내 문구 없음, 카메라·감지기 정상, `S` 사이클·자원 0
- 가짜 카메라: **9/9 통과**, 종료 코드 0. 효과는 `608x1080 (preview x0.5, px scale 0.563); 24 drawings/s`.
- 실제 카메라(`--camera real`): **7/9.** `S` 사이클이 들어 있는 시나리오 2개("S 수동 한 사이클", "효과 WebGL2 생성 실패")가 `timeout waiting for idle`로 실패했다.
  - 원인: OBS 화면 앞에 사람이 있어 쿨타임 직후 자동 회차가 시작된다. 그래서 확인 도구가 대기 상태를 보지 못했다.
  - 이번 변경과 무관하다. 같은 조건에서 `689f261`(임시 detached worktree, 확인 뒤 제거)도 "S 수동 한 사이클"이 같은 이유로 실패했다(6/7).
  - 효과 시나리오는 실제 카메라에서도 통과했다(`540x960`, 24장/초, 컨텍스트 손실·복구). 이 한계를 SYSTEM 1절과 README에 적었다.

### 정리

- 확인 도구·임시 스크립트가 띄운 Chrome·서버를 모두 종료했다. 임시 프로필, 받은 원본 폴더, 하네스 폴더(합성 PNG 포함), 임시 worktree를 지웠다. 사용자 OBS(PID 60536)는 그대로다. 저장소 루트 `config/`·`logs/`는 생기지 않았다.

### 미검증

- 4K 카메라 입력(2160×3840)에서의 실시간 미리보기. 하네스에서 4K 렌더 시간(약 10ms, 정지 이미지)만 쟀다.
- 현장 PC 성능, 키오스크 화면(`--kiosk`, 비 headless)에서의 표시, 효과를 켠 장시간 실측.
- 실제 GPU 장애로 생기는 컨텍스트 손실(`WEBGL_lose_context`로 흉내 냄), `EXT_color_buffer_float`가 없는 GPU, 셰이더 컴파일 실패 경로(Node 테스트의 가짜 렌더러로만 확인).
- 사람이 실제 화면을 보고 원본 필터와 같은지 판단하는 것. 원본 페이지에 카메라 입력이 없어 실제 카메라로는 원본과 나란히 비교하지 않았다. 합성 이미지에서는 화소가 같다.

## 남은 문제

- **메인 스레드 비용:** 그림 한 장에 CPU 약 6.5ms(획 목록 생성·정렬·합치기·GPU로 4MB 올리기)이고, 24장/초면 메인 스레드의 약 16%다. 개발 PC에서는 화면·감지에 영향이 없었다. 현장 PC가 느리면 `fps`를 낮추거나, 획 목록을 Worker로 옮기거나 미리 만들어 두는 방법을 검토한다.
- **0.5배 미리보기는 최종 해상도보다 부드럽다**(위 수치). 미리보기 = 촬영 결과를 엄격히 맞추려면 `previewScale` 1(OBS 1080이면 비트 단위로 같은 그림)이 필요하다.
- **4K 입력이면 미리보기(1080, s = 1)와 촬영 결과(2160, s = 2)가 다른 해상도라** 같은 구성이지만 결과가 더 세밀하다(PSNR 약 23dB). 5-2에서 결과를 어느 해상도로 그릴지 정해야 한다.
- 촬영 결과에는 아직 효과가 없다(5-2).
- `npm run check:browser -- --camera real`은 화면 앞에 사람이 있으면 `S` 사이클 시나리오가 실패한다(이전부터). 확인 도구가 `P`를 켜고 돌게 바꿀 수 있다(범위 밖, 제안만).

1. **원본 필터 코드의 사용 권한:** 페이지·사이트에 라이선스 표기가 없다. 사용자(또는 갤러리 제작자)가 이 코드를 이 프로젝트에 쓰는 것을 허락한 것인지 확인이 필요하다. 출처 표기는 파일 머리말에 남겼다.

3. **촬영 결과 해상도(5-2):** 4K 입력이면 결과를 2160×3840(s = 2, 더 세밀)으로 그릴지, 미리보기와 같은 1080 기준으로 그려 키울지.
