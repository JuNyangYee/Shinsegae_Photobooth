## 결정과 이유

### 파이프라인

```text
카메라 프레임 → 9:16 cover 크롭·좌우 반전 + 입력 회색조(Rec.709)   FS_INPUT_GRAY (그리는 해상도 RGBA8)
  → oil2f 패스 그대로 (색 보정 → … → 합성)
  → 출력 단계 회색조·레벨 (6-1 FS_OUTPUT, Rec.601) → 화면 / 결과 1080×1920 JPEG
결과 사진만: 같은 합성 그림 → 6-1 톤 점 경로(면적 평균 → 블루 노이즈) → 인쇄용 1비트 576×1024
```

- 입력 회색조는 **유화 첫 패스(색 보정) 앞의 패스 하나**다. 크롭·반전은 이 패스가 하고, 색 보정은 회색 그림을 크롭·반전 없이(오프셋 0, 배율 1) 텍셀 가운데에서 읽는다. 원본 페이지에 회색 이미지를 넣고 그리는 것과 같은 읽기다. `FS_GRADE`에 회색조를 넣는 방법도 있었지만 원본 셰이더를 고치게 되어 고르지 않았다.
- 회색 그림은 RGBA8(8비트)이다. "단순 흑백 이미지 한 장"과 같은 뜻이 되고, 다음 패스가 원본과 같은 형식의 입력을 읽는다.

### 입력 회색조 계수: Rec.709 luma (0.2126, 0.7152, 0.0722)

- 카메라·OBS 영상은 sRGB/BT.709 원색이므로 그 원색의 밝기 비율이 맞다. Rec.601(기존 `lum`, 0.299·0.587·0.114)은 옛 NTSC 원색 기준이라 빨강을 더 밝게, 초록을 덜 밝게 본다(빨강 0.299 vs 0.2126).
- 감마 보정된 값에 바로 곱하는 luma다. 선형으로 바꿔 휘도를 구하는 것보다 단순하고, 7-1 이전부터 회색조는 모두 감마 값에 계수를 곱했다.
- 계수 합이 1이라 이미 회색인 화소는 그대로다(Node 테스트: 0~255 전부).
- 셰이더는 계수를 uniform으로 받는다. 숫자를 한 곳(`core/thermal.js`)에만 둔다.
- 출력 단계 회색조(Rec.601)는 6-1 그대로 두었다. 들어오는 그림이 거의 무채색(채도 최대 25)이라 계수 차이가 결과에 거의 없다.

### 무채색 처리: (b) 마지막에 다시 회색조, `grade` 기본값 1 그대로

회색 입력을 `oil2f`에 넣은 결과(이식본 컬러 경로, 합성 이미지 2장 1080×1920, 아래 "원본과의 관계"로 원본과 같은 경로)의 채도를 쟀다. 채도 = 화소의 RGB 최댓값 − 최솟값.

| 조건 | 채도 최대 | 채도 평균 | 채도 > 2인 화소 | 평균 R−G / B−G |
|---|---|---|---|---|
| 기본값 (`grade` 1), seed 0·7, boil 0.1 | 24~25 | 9.1~9.9 | 84~100% | +3.8 / −5.3~−6.1 |
| 강도 1·붓 크기 1 | 34~35 | 8.6~9.4 | 82~100% | +3.5~3.7 / −5.0~−5.8 |
| `grade` 0 | 3 | 0.22~0.24 | 0% | 0 / 0 |
| **회색조 유화 (b)** | **0** | 0 | 0% | 0 / 0 |

- 원인: 색 보정(R×1.035, B×0.94, 갈색 3%)이 회색에 세피아 톤을 입힌다. `grade` 0이어도 획 색 흔들림(`VS_STROKE`가 R·B를 반대로 0.5×흔들림)이 최대 3을 남긴다.
- (a) `grade` 기본값 0: 무채색이 되지 않고(최대 3), 색 보정이 하는 밝은 곳 압축까지 빠져 원본 유화 톤이 바뀐다. 원본 기본값도 바뀐다.
- **(b)를 골랐다:** 원본 패스·기본값을 그대로 두고, 이미 있는 출력 단계 회색조(6-1 `gray` 모드와 같은 패스)로 모든 화소를 R=G=B로 만든다. 새 셰이더가 필요 없다. 세피아가 밝기로 바뀌는 차이는 계수상 0.3~0.4%다.
- 측정: 미리보기 채도 0(실제 OBS 10그림, 가짜 카메라, 합성 이미지), 결과 JPEG 채도 0(실제 OBS·가짜 카메라).

### 원본과의 관계

- **원본 페이지를 다시 받아 직접 비교하지 못했다.** 저장소 밖 새 빈 폴더에 배포 페이지를 받으려 했으나, 이 환경의 권한 분류기가 외부 코드 받기를 막았다. `%TEMP%`에 10-16 분석 때 추출된 원본 스크립트 사본(`nau-oil-analysis-20261016\app.js`)이 있지만, 같은 성격(외부 코드를 브라우저에서 실행)이라 허락 없이 실행하지 않았다. 아래 "질문"에 남긴다.
- 대신 우리 코드만으로 등가를 확인했다(저장소 밖 임시 하네스, 합성 이미지 2장 × 반전 없음·반전 × 매개변수·seed 5가지, RTX 5090·ANGLE D3D11):
  1. `FS_INPUT_GRAY`를 렌더러와 같은 방식(소스 위아래 뒤집어 올림, LINEAR, 전체 화면 삼각형)으로 따로 그려 **GPU 입력 회색 그림**을 읽었다. 모든 화소가 R=G=B였다.
  2. 그 회색 그림을 **컬러 유화 경로**(`outputMode: 'off'`)에 넣었다. 이 경로는 5-1에서 원본 페이지와 화소가 완전히 같음을 확인한 이식본이다(로그 2026-10-16-02, 7단계 검수의 smoothstep 수정 뒤에도 실행 사이 ±1 잡음 안). 즉 "원본 페이지에 회색 이미지를 넣은 결과"와 같은 것이다.
  3. 그 결과를 CPU로 회색조(Rec.601·레벨)로 바꿔 회색조 유화(컬러 입력)와 비교했다: **최대 차이 1**(화소 4~12%, 마지막 회색조의 GPU float·CPU 반올림 차이), `grade` 0이면 **0**. 획 배치·그림 구조는 같다.
- **알게 된 것:** CPU `inputGrayOf`(float64, `Math.round`)는 GPU 입력 회색과 화소 1.3~1.7%에서 ±1 다르다. 유화는 이 작은 차이에도 보완 층(칸의 오차 최대 위치)·세부 문턱 판정이 바뀌어 획 배치가 달라진다(CPU 회색을 넣으면 화소 35%까지, 최대 122 차이). 그래서 "회색 이미지"는 GPU 패스가 만든 것을 기준으로 한다. 원본 페이지와 직접 비교할 때도 이 GPU 회색 그림을 PNG로 넣어야 같은 그림이 나온다. CPU 식은 효과를 그리지 못했을 때의 대체 경로에만 쓴다.
- 참고: 컬러 유화 → 회색조(기존 `gray` 모드)와 회색조 유화는 같은 seed에서 평균 4.4~8.1/255 다르다. 회색 입력에서는 밝기가 같은 색 경계(빨강·초록)가 흐름장·세부 판정에서 사라진다.

### 기본값·`E`·호환

- `OUTPUT_MODES = ['gray-oil', 'thermal', 'gray', 'off']`, 기본값 `gray-oil`. 감열지·회색조·컬러는 지우지 않았다.
- `E`: 출력 모드 첫 선택지 "회색조 유화 (흑백 → 유화)". 감열지가 아니면 흑백 스타일·질감 세기·선 간격을 막는다. 회색조 유화에서 점 방식·용지 폭은 결과의 인쇄 데이터에 쓰여 연다(붓 결 선이 골라져 있어도). 레벨은 끔이 아니면 쓴다. 실시간 줄: `회색조 유화 · 인쇄 데이터 576점 폭 블루 노이즈 (촬영 때)`.
- 붓 결 선 관련 기본값(`bwStyle` stroke·간격 4·질감 1)은 그대로이고 감열지 모드를 고를 때만 쓰인다.
- **저장 형식:** 키·버전(1)은 그대로이고 `outputMode` 값만 늘었다. 파일에 모드가 있으면 그 값을 쓴다(7단계 파일 → 감열지 그대로, 알림 없음). 모드가 없는 5-2 파일 → 새 기본값 회색조 유화. 값이 틀린 파일 → 그 항목만 기본값. 예전 코드가 `gray-oil` 파일을 읽으면 그 항목만 예전 기본값(감열지)이 된다.
  - **현장 주의:** 7단계 이전에 `E`에서 저장한 파일이 있으면 회색조 유화가 아니라 감열지로 시작한다. 바꾸려면 `E`에서 회색조 유화를 고르고 저장한다.
- `boil` 0.05는 그대로다(질문).

### 결과 사진

- **형식: 1080×1920 JPEG**(기존 `config.capture`, 품질 0.92, 실제 OBS 약 463KB). 연속 톤 그림이라 JPEG가 맞고, 화면 표시용이라 무손실이 필요 없다(1비트 정본은 따로 있다). PNG면 합성 인물에서 약 2.3MB이고 인코딩도 길다.
- 셔터 순간 미리보기와 같은 그림: 같은 프레임·tick·seed·설정을 같은 렌더러로 그린다(5-2 규칙 그대로). 블록 평균 차이 0.072~0.073/255(다른 그림 0.60~11.8).
- **인쇄용 1비트**(6-1 형식 그대로: 래스터 비트·1비트 PNG·`blackRatio` 등): 렌더러가 결과 렌더에서 같은 합성 그림을 6-1 **톤 점 경로**(회색조·레벨 → 면적 평균 → 점 방식)로 만든다. 결과 JPEG 화소를 CPU로 다시 줄이는 방법보다 동기 구간이 짧고(GPU 패스 2개, 4분의 1 크기 읽기 2번), 6-1의 GPU = CPU 확인(`gpu=cpu`)을 그대로 쓴다. 흑백 스타일(선)은 쓰지 않는다. 점 방식·용지 폭은 `E`의 `dither`·`paperDots`. 레벨은 화면과 같은 값이다.
- **인쇄 데이터 미리보기는 넣지 않았다.** 인쇄 연동이 없고, 화면에 보이지 않는 데이터의 모양은 실제 용지로 확인해야 의미가 있다. 결과마다 보여 주려면 Object URL·캔버스 자원이 하나 더 생겨 정리 규칙이 늘어난다. 숫자(크기·검은 점 비율·PNG 크기)는 D `print` 줄에 있다. 합성 인물의 인쇄 1비트 그림은 사용자 확인용 폴더에 넣었다(아래).
- **실패 규칙:** 기존 규칙을 따르되 하나를 정했다. 회색조 유화에서 **인쇄 데이터만 실패하면 사진은 그대로 두고 인쇄 데이터 없이** 보인다(경고, D `print none (원인)`). 감열지는 화면용 사진이 마스크에서 나와 원본 컬러로 대신했지만, 회색조 유화 사진은 인쇄 데이터와 관계없이 맞기 때문이다. 효과를 그리지 못하면 원본 사진(결과 크기)에 CPU 입력 회색조·레벨, 인쇄 데이터도 그 사진에서(`RAW PHOTO gray-oil 1080x1920`). 회색 변환까지 실패하면 원본 컬러. 비동기 처리·취소·늦은 결과 폐기·자원 해제는 그대로이고, 인쇄 처리 중 취소되면 사진 캔버스를 비우고 끝낸다.

### 결과 출력물 표시 크기: 50cqw (연속 톤), 53.333cqw (1비트 점)

- 576/1080 폭(1:1)은 1비트 점을 화면 화소에 맞추기 위한 것이었다. 회색조 유화 1080×1920을 그 폭에 놓으면 1080 화면에서 0.533배, 4K에서 1.067배라 비정수 배율 보간이 된다.
- **50cqw**: 1080 폭 화면에서 정확히 1/2(540px), 4K(2160) 화면에서 1:1. 1080 화면에서 Chrome이 2×2 상자 평균으로 줄인다: 화면 화소와 결과 사진의 2×2 평균 차이 평균 0.375·최대 0.75(반올림 수준, 가짜 카메라 화면 그림에서 잼). 최근접(2×2 중 한 화소)과의 차이는 평균 1.9였다. 사진 왼쪽·위가 정수 화소(270, 440)에 놓인다.
- 출력물이 6% 작아지지만 카드·여백·진행선·안내 위치는 7-2 그대로다.
- 사진의 `dots`(결과 단계가 정함)로 고른다. 감열지 결과는 `dots: true` → `is-dots` → 53.333cqw(6-3 그대로).

### 첫 촬영 긴 작업 (측정 중 발견, 고침)

- 처음 구현에서 실제 OBS 첫 촬영의 동기 구간이 **54.6ms, 긴 작업 1개(rAF 66.7ms)**였다. 회색조 유화 미리보기는 인쇄 경로를 쓰지 않아, 블루 노이즈 문턱 지도 만들기(약 25ms, 처음 쓸 때 한 번)·인쇄 대상 할당·축소·디더 셰이더 첫 사용이 첫 셔터에 몰렸다.
- 렌더러가 회색조 유화 미리보기에서 **용지·점 방식이 바뀔 때 한 번** 인쇄 대상·문턱 지도를 만들고 축소·디더 패스를 그린다(화소는 읽지 않는다). 그다음 3번째 촬영에 50ms 긴 작업이 한 번 남아, 결과 단계가 인쇄 처리(GPU = CPU 확인·비트 묶기·PNG) 앞에서 작업을 한 번 양보하게 했다. 결과: 3회 동기 구간 16.6~26ms, 긴 작업 0(아래 "성능").

## 남은 문제

- 회색조 유화의 인쇄 데이터는 화면용 레벨(밝기·대비·감마)을 그대로 쓴다. 실제 용지에서 다른 보정이 필요하면 인쇄 연동 때 인쇄 전용 레벨을 따로 둘지 정한다.
- 결과 사진 동기 구간이 감열지보다 5~10ms 길다(결과 화소 8MB 읽기). 긴 작업은 없지만 현장 PC에서 다시 본다.
- 6·7단계 남은 문제(실제 프린터, 점 방식 최종 확정, 첫 카운트다운 긴 프레임 현장 확인)는 그대로다.
