## 결정과 이유

- **강제 초기화(`X`)에는 쿨타임을 두지 않는다.**
  - 쿨타임은 방금 결과를 본 사람이 같은 자리에서 바로 다시 찍히는 것을 막는 장치다.
  - 강제 초기화는 운영자가 꼬인 진행을 풀거나 시험할 때 쓴다. 운영자가 시작 시점을 직접 정하므로 완충이 필요 없고, 누른 즉시 다시 시작할 수 있는 편이 낫다.
  - 쿨타임 중에 누르면 남은 쿨타임도 없앤다. 회차를 올려 진행 중이던 사진 만들기 결과도 버린다.
- **카운트다운 취소(취소 요청·카메라 해제·페이지 숨김)에도 쿨타임을 두지 않는다.** 찍은 사진이 없으므로 막을 대상이 없다.
- **`capturing` 중에는 취소하지 않는다.**
  - 프레임은 이 상태에 들어가는 순간 동기로 이미 잡았다. 나머지는 효과·인코딩이며, 실측 약 30~50ms다.
  - 카메라가 이때 풀려도 결과를 보인다. "결과 중 카메라 해제 → 결과 유지"와 같은 이유다.
- **사진 만들기 실패나 `captureTimeoutMs`(5초, 가안) 초과는 쿨타임 없이 대기로 간다.**
  - 보여 줄 사진이 없기 때문이다.
  - 제한 시간은 효과·인코딩이 끝나지 않을 때 화면이 멈추지 않게 하는 안전값이다. 그 뒤 도착한 결과는 회차 검사로 버리고 바로 정리한다.
- **페이지가 숨겨져 있으면 시작 요청도 무시한다.** 숨김이 카운트다운을 취소하는 조건과 맞췄다.
- **결과 이미지는 JPEG 0.92 + Object URL로 만든다(가안).**
  - 인쇄를 연동하면 Blob을 그대로 넘길 수 있다.
  - 인코딩 뒤 캔버스를 바로 비워(크기 0) 큰 픽셀 버퍼를 오래 들고 있지 않는다.
  - 1080×1920 실측: 약 130~150KB, 인코딩 16~31ms.
  - PNG는 인코딩이 더 느리고 크다. 인쇄 규격이 정해지면 다시 본다.
- **CSP에 `img-src 'self' blob:`를 더했다.**
  - 첫 브라우저 실행에서 결과 `<img src="blob:...">`가 CSP에 막혔다(`securitypolicyviolation img-src blob`, `naturalWidth 0`). CSP의 `'self'`는 `blob:` 주소를 포함하지 않는다.
  - `blob:`은 같은 페이지가 만든 메모리 자료만 가리키므로 외부 전송이 아니다. `connect-src`는 그대로 `'self'`이고 `data:`는 넣지 않았다.
  - 대안은 캔버스를 그대로 보이는 것이었다. 그러면 인쇄용 Blob을 따로 만들어야 하고 지시의 Object URL 정리 규칙과도 어긋나서 택하지 않았다.
- **단축키 `S`(Start/Shoot)·`X`(초기화):**
  - 기존 `D`·`R`·`Esc`와 겹치지 않는다.
  - `Space`·`Enter`는 `R` 조절 화면의 버튼에 포커스가 있으면 그 버튼을 누르게 되므로 피했다.
  - 기존 규칙(수정 키 없이 한 키, 반복 입력 무시)을 따른다.
- **카운트다운 숫자는 시작 시각 기준으로 바꾼다.** 타이머가 늦게 불려도 늦음이 쌓이지 않는다(테스트로 확인).
- **결과 화면에서는 인식 표시와 카메라 상태 문구를 사진 위에 띄우지 않는다.**
  - 쿨타임에는 미리보기로 돌아가 위쪽에 "다음 촬영을 준비 중입니다."(가안)를 보인다.
  - 카메라가 준비되지 않았으면 이 문구 대신 기존 카메라 상태 문구를 보인다.
- **결과가 끝날 때 `<img>`의 `src`를 먼저 지우고, 그다음 Object URL을 `revoke`한다.** 상태 기계가 `notify()` 뒤에 `releasePhoto()`를 부른다.

| 결과·쿨타임·대기 중 카메라 미준비 | 결과 4.5초에 트랙 종료 + `getUserMedia`가 `NotReadableError`를 던지게 바꿈 | 카메라 `unavailable`인 동안(표본 231개) 결과 사진 유지, 사진 위 상태 문구·인식 표시 없음 → 13050ms 쿨타임(쿨타임 문구 대신 "준비 중" 문구) → 18065ms 대기 → `S` 무시(`start: camera-not-ready`) → `getUserMedia` 복구 → 다음 재시도에서 `ready` → `S` 받음 |
| 카운트다운 중 페이지 숨김 | `document.hidden`·`visibilityState` 덮어쓰기 + `visibilitychange` | 46ms 뒤 대기, `cancelled: page-hidden`. 숨김 중 `S` 무시(`start: page-hidden`), 보임으로 되돌린 뒤 `S` 받음 |

- 늦게 끝난 캡처 결과는 브라우저에서 재현하지 않았다. 인코딩이 수십 ms라 그 사이 `X`를 맞추기 어렵다. Node 테스트로만 확인했다.
- 4K(2160×3840) 캡처의 인코딩 시간과 용량은 측정하지 않았다(OBS 출력이 1080×1920). **미검증**.

## 사용자 실측 필요 (미실측)

사용 방법:

1. 서버를 띄우고 Chrome에서 `http://localhost:8765/`를 연다.
2. `S`를 눌러 촬영한다. 필요하면 `D`도 켠다.
3. 진행 중에는 `X`로 초기화한다.

## 남은 문제

- **D를 켠 채 결과를 보면 감지 박스가 결과 사진 위에 그려진다.** 개발용 화면이라 그대로 두었다. 불편하면 결과 중 겹쳐 그리기를 숨긴다.
- **결과 형식 JPEG 0.92는 가안이다.** 인쇄 규격이 정해지면 형식·품질을 다시 정한다.
- **`captureTimeoutMs` 5초는 가안이다.** 사진 효과가 정해지면 처리 시간 목표에 맞춘다. 효과가 길어지면 `capturing` 동안의 화면(진행 표시)도 필요하다.
- **결과 중 감지 루프는 계속 돈다.** 3-2에서 쿨타임 직후 바로 판정하려는 의도다. 부하가 문제면 4단계에서 본다.
- **자동 시작과 조절 화면:** 3-2에서 인식 결과로 자동 시작할 때 `R` 조절 화면이 열려 있으면 운영자가 범위를 맞추는 중에 촬영이 시작될 수 있다(아래 질문 3).

## 다음 작업

- **3-2 인식 결과로 자동 시작·이탈 시 취소.**
  - `presence.subscribe()`의 "인식됨"으로 `session.request('start', 'presence')`를 보낸다.
  - 카운트다운 중 "인식 안됨"이 되면 `session.request('cancel', 'presence')`를 보낸다. 짧은 누락은 인식 판정의 `absentGraceMs`가 흡수한다.
  - 쿨타임이 끝난 순간 이미 "인식됨"이면 바로 시작할지(상태 변화가 없어도) 정한다. 지금 인식 상태는 바뀔 때만 알린다.
  - 키보드 시작 완료와 감지 시작 완료를 구분해 보고한다(`docs/PROJECT.md` 4절).

## 질문

1. 운영 단축키 `S`(촬영 시작)·`X`(강제 초기화)가 괜찮을까요?
2. 쿨타임 문구 "다음 촬영을 준비 중입니다."(가안)를 둘까요, 아니면 쿨타임에는 아무 문구 없이 미리보기만 보일까요?
3. 3-2에서 `R` 조절 화면이 열려 있는 동안에는 자동 시작을 막을까요? (키보드 `S`는 계속 허용)
4. 결과 사진 형식은 인쇄가 정해질 때까지 JPEG(품질 0.92)로 두어도 될까요?

## 질문에 대한 결정 (오케스트레이터·사용자, 2026-10-15)

1. `S`·`X`를 그대로 쓴다.
2. 쿨타임 문구는 가안으로 둔다.
3. `R` 조절 화면이 열려 있는 동안 인식에 의한 자동 시작을 막는다. `S`는 허용한다.
4. 인쇄 규격이 정해질 때까지 JPEG 0.92로 둔다.
5. (다음 작업에서 짚은 점) 사용자 확정: 쿨타임 5초 뒤 스윗스팟이 비어 있지 않아도 진행한다. 자동 시작은 그 시점의 인식 상태로 판단하는 레벨 판정으로 만든다. 반영은 로그 08.
