## 결정과 이유

### 처리 순서와 축소 방식

- 순서는 지시대로다: 합성 → 회색조(Rec.601, 셰이더의 `lum`과 같음) → 대비·밝기·감마 → 인쇄 해상도로 축소 → 8비트 회색 → 1비트 디더 → 화면은 최근접 확대.
- 레벨 식: `v = clamp((lum − 0.5)·contrast + 0.5 + brightness, 0, 1)^(1/gamma)`. 대비 → 밝기 → 감마 순으로 둔 것은 가안이다(대비를 바꿔도 밝기 기준점이 움직이지 않게).
- **축소는 면적 평균**(점 하나가 덮는 원본 구간과의 겹친 넓이로 가중 평균).
  - 디더링은 "점 영역의 평균 밝기 → 점 밀도"라, 그 영역의 정확한 평균이 맞는 입력이다.
  - 1080 → 576은 1.875배다. 최근접·쌍선형은 원본 화소를 고르지 않게 건너뛰어 톤 오차·모아레가 생기고, 정수 칸 박스 필터는 이 배율에 맞지 않는다. 면적 평균은 모든 원본 화소를 정확한 비율로 한 번씩 센다.
  - 결과를 가로 4점씩 RGBA8에 묶어 화소 읽기가 576×1024 대신 144×1024(590KB)다.

### 점 방식 비교와 기본값 (제안: 블루 노이즈)

실제 OBS 1080×1920, 미리보기 1배·24장/초, 방식마다 10초(아래 "검증"의 측정 방법).

| | 블루 노이즈 | Bayer | Atkinson | Floyd–Steinberg |
|---|---|---|---|---|
| 어디서 | GPU 문턱값 | GPU 문턱값 | CPU 오차 확산 | CPU 오차 확산 |
| 그리기 CPU 평균 (끔 7.9ms) | 7.6ms | 7.6ms | 14.3ms (읽기 2.5 + 디더 4.0) | 15.1ms (읽기 2.3 + 디더 4.6) |
| 메인 스레드 (끔 33%) | 31% | 31% | 48% | 48% |
| 감지 | 15fps | 15fps | 13.8fps | 12.8fps |
| 그림 사이에 바뀐 점 | 0.6% | 0.6% | 16.7% | 27.0% |
| 흐림(σ 1.5점)으로 본 톤 PSNR / 평균 밝기 치우침 | 27.0dB / 0 | 26.9dB / +0.008 | 22.6dB / −0.030 | 28.9dB / 0 |
| 화질 인상 (합성 시험 도표) | 무늬 없이 고르고 매끈하다. 경사가 자연스럽다 | 격자(십자) 무늬가 눈에 띈다. 인쇄물 같은 규칙적인 느낌 | 대비가 강하고 어두운 곳이 뭉개진다. 밝은 곳은 날아간다. "감열지다운" 강한 인상 | 톤이 가장 정확하고 세부가 많다. 오차 확산 특유의 지렁이 무늬가 조금 |

- 비용: 문턱값 방식은 화소를 읽지 않아 효과를 끈 것과 같다. 오차 확산은 그림마다 동기 화소 읽기 + CPU 디더(576×1024에서 4~5ms)가 더해진다. 24장/초면 메인 스레드가 1.5배가 되고 감지가 15fps 아래로 떨어졌다. 개발 PC(RTX 5090)에서 이 정도라 현장 PC에서는 더 나빠진다.
- 깜빡임: 오차 확산은 회색이 조금만 바뀌어도 오차가 줄 전체로 퍼져 점 배치가 크게 바뀐다. 유화의 획 다시 그리기(boil)와 겹쳐 미리보기가 계속 지글거린다(17~27%의 점이 그림마다 바뀜). 문턱값 방식은 문턱 지도가 고정이라 바뀐 곳만 바뀐다(0.6%).
- **제안 기본값: 블루 노이즈.** 미리보기가 안정적이고(관람객이 보는 화면이 곧 출력물이므로 지글거림이 그대로 보인다), 비용이 효과 끔과 같고, 톤 치우침이 없다. 결과 사진 한 장만 보면 Floyd–Steinberg의 톤이 조금 더 정확하지만, "화면 = 출력물" 원칙 때문에 미리보기와 같은 방식을 써야 한다.
- 실제 감열지에서는 점이 번져 어두워진다. 블루 노이즈는 흩어진 낱점이 많아 번짐에 약할 수 있다. 실제 프린터로 비교해 최종 확정해야 한다(TBD, 아래 질문).

### 블루 노이즈 문턱 지도

- 저장소에 텍스처를 두지 않고 시작할 때 코드로 만든다(void-and-cluster, 64×64, 가우스 σ 1.5, 토러스, 처음 배치는 고정 seed mulberry32 10%, 같은 값이면 앞 번호). 개발 PC 약 25ms, 처음 쓸 때 한 번이다.
- 문턱 규칙 `t = 1 + floor(r·255/N)`, `g ≥ t`면 흰 점: 회색 0은 모두 검정, 255는 모두 흰색, 흰 점 수는 `ceil(g·N/255)`(Node 테스트). 8비트 정수끼리 비교라 GPU와 CPU가 비트 단위로 같다.
- 문턱 지도는 고정이고 그림마다 바꾸지 않는다. 같은 seed·프레임이면 결과가 같다(결정성). 그림마다 문턱을 흔들면 정지 장면에서도 지글거린다.

### 화면 표현

- 감열지 모드의 효과 캔버스는 인쇄 해상도이고 CSS `image-rendering: pixelated`로 최근접 확대한다. `style.css`를 건드리지 않으려고 `effect-preview.js`가 캔버스의 inline style에, `main.js`가 결과 `<img>`의 inline style에 넣었다.
- 1080 폭 화면에서 1.875배라 점 폭이 1·2화소로 섞인다. 정수배가 아니라 생기는 일이다(아래 질문 2).
- 종이색 `[246,242,233]`·잉크색 `[26,26,30]`은 가안이고 `config.thermalDisplay`다. 화면 표시에만 쓴다.

### 촬영 결과

- (a) **인쇄용 1비트 데이터가 정본**이다: 래스터 비트(줄마다 72바이트, 1 = 검은 점, ESC/POS `GS v 0`과 같은 뜻) + 1비트 회색조 PNG Blob. 사진 객체의 `print`로 메모리에만 둔다.
- (b) 화면용은 (a)의 마스크를 종이색·잉크색으로 칠한 PNG다. 미리보기 캔버스와 같은 색 값이라 셔터 직전 그림과 화소가 같다(브라우저 확인).
- PNG 압축은 브라우저 내장 `CompressionStream('deflate')`(zlib 형식)이다. 외부 라이브러리·전송 없음. 비동기라 셔터 순간 동기 구간에 들어가지 않는다.
- 문턱값 방식이면 결과 마스크를 GPU에서 읽고(화면과 같은 패스), 같은 회색으로 CPU 계산을 한 번 더 해 비교한다(D `gpu=cpu`). 다르면 경고하고 GPU 쪽을 쓴다. 현장 GPU 드라이버의 정밀도 문제를 실제 결과마다 알아챌 수 있게 했다(촬영마다 약 1~2ms, 비동기 압축 전).
- 형식: 감열지 → PNG + 인쇄 데이터, 회색조·끔 → 기존 JPEG.
- 회색조 모드는 점 없이 결과 크기(1080×1920) 회색 이미지라 JPEG로 두고 인쇄 데이터를 만들지 않았다(가안, 질문 3).

### 실패 대체

- **유화 효과를 그리지 못하면 원본 사진에 같은 출력 단계를 CPU로 적용한다**(원본 화소 → 레벨 → 면적 평균 → 같은 점 방식, 인쇄 데이터 포함).
  - 이유: 관람객 흐름은 끊지 않는다(5-2 규칙). 감열지 출력물 모양이 같고, 인쇄 연동 때 인쇄할 데이터가 있다. CPU 함수는 GPU 문턱값과 같은 식이라 점 방식도 같다.
  - 이 경우 미리보기는 원본 컬러였는데 결과는 흑백 점이다. 5-2부터 장애 중에는 미리보기·결과가 원본이었고, 출력물이 감열지이므로 결과를 감열지로 두었다(질문 4).
- **출력 단계 자체가 실패하면**(PNG 압축·캔버스 등) 원본 컬러 사진(결과 크기, JPEG), 인쇄 데이터 없음. 더 고칠 수단이 없고 드문 경우다.
- `config.effect.enabled` false면 예전처럼 원본 그대로이고 출력 단계도 쓰지 않는다.

### 설정·저장

- `config.effect`에 6개 값, `effectLimits`·`OUTPUT_MODES`·`DITHER_METHODS`. 용지 점 수는 128~1024의 8의 배수로 맞춘다.
- 저장 파일은 **버전 1 그대로** 13개 값. 5-2 파일(7개)을 읽으면 그 값을 쓰고 나머지 6개는 기본값(감열지)으로 채워 "없는 키" 알림을 남긴다(기존 규칙). 운영자가 한 번 저장하면 사라진다.
- `E`에서 회색조면 점 방식·용지 폭, 끔이면 레벨도 막는다(쓰지 않는 값). 용지 폭 선택지는 576·384 두 개이고, 파일에 다른 8의 배수가 있으면 값 표시(`512점`)로 보인다.

- 출력 모드 3단계: 끔·회색조 결과 1080×1920 JPEG(`print -`), 감열지 Bayer 캔버스 576×1024, 감열지 Atkinson(CPU) 결과도 셔터 직전 그림과 화소 차이 0. 용지 384점·감마 1.3 저장 → 새로고침 뒤 캔버스 `384x683 pixelated`, 파일 `version` 1에 출력 값.
- GPU = CPU: 합성 이미지에서 576×1024·384×683 × Bayer·블루 노이즈 모두 **0/589,824·0/262,272 다름**. 1비트 PNG를 브라우저가 디코드한 화소 = 마스크(0 다름), IHDR 깊이 1·색 형식 0.
- 실패 3가지(예외·`INVALID_OPERATION`·손실): 모두 `RAW PHOTO thermal 576x1024 (원인)`과 `print 576x1024 1-bit`, 자원 0, 미리보기 다시 `running`. WebGL2 생성 실패도 `RAW PHOTO thermal`.
- 외부 요청·CSP 위반·페이지 예외 0.

### 실제 OBS 카메라 (임시 프로필 headless Chrome, 저장소 밖 임시 스크립트, 이미지 저장 없음)

- 측정 방법: 앱을 열고 `P`(자동 촬영 일시정지), `E`를 열어 선택 상자로 모드·방식을 바꾸고 3초 뒤 10초 동안 D 화면(1초마다)·rAF 간격·긴 작업·CDP `TaskDuration`을 쟀다. 끝나면 `E`를 저장하지 않고 닫았다(조절값 파일은 측정 전후 "없음"으로 확인).
- 비용 표는 위 "점 방식 비교"와 SYSTEM 6절 "출력 단계"의 성능 표. 모든 경우 rAF 60fps, 25ms 넘는 간격 0, 긴 작업 0, 초당 24장.
- 깜빡임·톤: 페이지 안에서 렌더러를 하나 더 만들어 실제 영상 24그림(42ms 간격, seed 증가)의 회색을 읽고 네 방식 마스크를 계산했다(GPU Bayer = CPU Bayer도 매 그림 확인). 이 동안 장면 움직임은 작았다(그림 사이 회색이 바뀐 점 5.3%). 가짜 카메라(움직이는 시험 영상, 회색 변화 10.4%)에서는 바뀐 점이 블루 노이즈 3.7%, Bayer 3.7%, Atkinson 40%, Floyd–Steinberg 44%였다.
- **촬영 순간 끊김**(블루 노이즈, `S` 3회): 동기 구간 15.9·14.2·12.9ms, 전체(PNG 압축 포함) 64·43·34ms. rAF 최대 33.3·16.9·17.0ms(25ms 넘는 간격 1·0·0), 긴 작업 0. 5-2(컬러 JPEG)와 같은 수준이다.
- 모드 3단계 전환·방식 전환·`E` 저장·새로고침 유지는 위 확인 도구 실제 카메라 모드로 확인했다.
- 화질 인상은 **합성 시험 도표**(경사·얼굴 모양 도형·글자·가는 선, 카메라 영상 아님)를 네 방식으로 그린 그림을 `%TEMP%`에 잠깐 써서 보고 지웠다. 카메라 영상은 보지도 저장하지도 않았다.

### 정리

- 확인 도구·측정 스크립트가 띄운 Chrome·서버를 모두 종료하고 임시 프로필·임시 스크립트 폴더를 지웠다. 저장소 `config/`·`logs/`는 없다. 사용자 OBS는 그대로다.

### 미검증

- **실제 감열지 프린터 출력.** 화면의 점 그림이 실제 용지에서 같은 톤으로 나오는지(점 번짐, 밝기·감마 보정), 방식별 실제 인쇄 화질. 인쇄 연동은 범위 밖이다.
- 사람이 키오스크 화면(비 headless, 실제 세로 모니터)에서 점 그림을 보는 인상, 1.875배 최근접 확대의 점 폭 차이가 눈에 띄는지.
- 화면 앞에서 사람이 움직일 때의 깜빡임. 실측 때 장면 움직임이 작았다(회색 변화 5.3%).
- 현장 PC 성능, 4K 입력, 장시간 실측(감열지 기본값).
- 58mm(384점) 프린터 실제 출력.

## 남은 문제

- 점 방식 기본값은 측정·합성 도표로 정한 **가안**이다. 실제 프린터 출력으로 확정해야 한다.
- 오차 확산은 미리보기 비용(메인 스레드 1.5배, 감지 13~14fps)과 깜빡임이 크다. 고를 수는 있지만 현장에서는 권하지 않는다. 필요하면 Worker로 옮기거나 결과 사진에만 쓰는 방법이 있지만 "화면 = 출력물" 원칙과 맞지 않는다.
- 화면 확대가 1.875배(1080 폭)라 점 폭이 1·2화소로 섞인다. 4K 세로 화면이면 3.75배다.
- 결과 사진의 동기 구간은 13~16ms(5-2와 같은 수준)이고 3회 중 1회 한 프레임이 밀렸다.
- 5단계 남은 문제(원본 필터 사용 권한 확인, 획 목록 CPU 비용)는 그대로다.

## 다른 브랜치와 겹치는 곳 (`stage6-guest-ui`)

- `src/web/index.html`: **효과 조절 패널(`#effect-panel`)만** 고쳤다(제목, 출력 항목 6줄). 관람객 화면 요소는 그대로다.
- `src/web/main.js`: 결과 사진을 넣는 `renderSession`에 한 줄(`resultImage.style.imageRendering`, 감열지 결과면 `pixelated`)을 더했다. 그 밖은 D 화면 줄(`effectDevLines`·`sessionDevLines`)이다.
- `src/web/style.css`는 건드리지 않았다. 결과 화면 레이아웃을 바꿀 때 결과 `<img>`의 `image-rendering`이 inline style로 들어간다는 점만 알면 된다.
