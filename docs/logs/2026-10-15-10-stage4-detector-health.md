# 2026-10-15-10 — 4-1 감지기 안정성과 장애 안내

브랜치 `stage4-stabilize`(`master` `c7b0a15`에서 분기). 작업 에이전트(Opus 5.5)가 오케스트레이터가 지정한 4-1만 했다. 대상은 전체 검수 F4·F5(로그 09)와 4단계 항목 "Chrome 하드웨어 가속(WebGL) 점검"의 웹 쪽이다. 실행 스크립트(`bin/`, `Launch.bat`, `settings*`)는 다른 브랜치(`stage4-launch`)의 범위라 건드리지 않았다. 작업 도중 세션 한도로 한 번 끊겼다가 이어서 마쳤다.

## 원인 조사: MediaPipe 1.1.1 생성 실패 누적 (F4)

번들 `vision_bundle.mjs`의 `createFromOptions` → 내부 `createTaskRunner` 흐름을 읽고, 브라우저에서 수치를 쟀다.

1. 생성할 때마다 wasm 로더 JS를 `<script>`로 `document.body`에 붙인다. 지우지는 않는다.
2. 로더가 만든 전역 `ModuleFactory`로 wasm 인스턴스를 새로 만든 뒤, 라이브러리가 `ModuleFactory`를 바로 지운다. 그래서 로더·wasm을 다음 생성에 다시 쓸 공개 방법이 없다. `FilesetResolver.forVisionTasks()`는 경로만 돌려주므로, 한 번만 불러와 재사용해도 누적은 줄지 않는다. 지금 코드도 bundle 모듈은 이미 한 번만 불러온다.
3. 태스크 객체를 만든 직후, 모델 설정(`setOptions`: 모델 받기·그래프 시작)보다 **먼저** 사용 통계 로거를 만든다. 이 로거는 60초 `setInterval`이다. 모델 설정이 실패하면 이 로거를 닫지 않는다.
4. `FaceDetector.createFromOptions`는 클래스를 고정해 부른다. 그래서 하위 클래스로 실패한 인스턴스를 받아 `close()`할 수 없다.

- GPU·CPU 두 delegate를 차례로 시도하므로, 실패 1회마다 타이머 +2, `<script>` +2다. 검수자가 잰 "3번 시도에 타이머 +6, 스크립트 2→8"과 맞는다.
- WebGL이 아예 없으면 다르게 쌓인다. GPU 생성은 실패하고(누적 +1), CPU 생성은 성공한다. 그 감지기는 매 프레임 감지에 실패해 15회 뒤 버려지고, 15초 뒤 같은 일이 되풀이된다.

## 결정과 이유

### 1. 생성 실패 자원 누적 (F4)

막기와 정리를 함께 했다. 막기는 흔한 원인(모델·WebGL)이 MediaPipe 생성까지 가지 않게 하는 것이다. 정리는 그래도 생성이 실패할 때(원인 불명) 남는 것을 지우는 것이다.

- **사전 확인 (`face-detector.js`):**
  - WebGL: 1×1 `OffscreenCanvas`로 `webgl2`, 없으면 `webgl` 컨텍스트를 만들어 본다. 확인용 컨텍스트는 바로 놓는다.
  - 모델: HTTP 상태·크기·SHA-256을 확인한다. 기준값은 `config.faceDetection.modelBytes`·`modelSha256`이고, `tools/vendor-mediapipe.mjs` 기록과 같다. 테스트가 실제 파일과도 대조한다.
  - 둘 중 하나라도 실패하면 bundle·로더·wasm·타이머를 아예 만들지 않는다.
- **확인한 바이트를 넘긴다:** `modelAssetBuffer`(복사본)로 넘기므로 생성 중에 모델 받기가 실패할 수 없다. 통과한 바이트는 기억해서 다시 받지 않는다(약 225KB).
- **실패 정리:**
  - MediaPipe가 쓸 GL 캔버스를 직접 만들어 `canvas` 옵션으로 넘긴다. 라이브러리 기본값과 같은 1×1 `OffscreenCanvas`이고, 실패하면 그 컨텍스트를 `WEBGL_lose_context`로 놓는다. 페이지당 WebGL 컨텍스트 수에 상한이 있어, 실패한 컨텍스트가 쌓이면 살아 있는 감지기의 컨텍스트가 밀려날 수 있기 때문이다.
  - 생성하는 동안만 `setInterval`을 감싸 60초 간격 타이머만 기록하고, 실패하면 지운다. 생성이 끝나면 되돌린다.
  - 성공·실패와 관계없이 실행이 끝난 로더 `<script>` 요소를 지운다.
  - **한계:** 타이머 기록은 1.1.1 내부 동작(로거 간격 60000ms)에 기대는 우회다. 버전을 올리면 다시 확인해야 한다. 이 내용은 `docs/SYSTEM.md` 5절에 적었다. 전역 프로토타입은 바꾸지 않았고, 캔버스는 인스턴스의 `getContext`만 감쌌다.
- **재시도 간격 (`detector-keeper.js`):**
  - 15초부터 연속 실패마다 두 배, 최대 300초다: 15·30·60·120·240·300초(가안, `detectorRetryMaxMs`). 상한을 둔 이유는 운영자가 원인을 고친 뒤 너무 오래 기다리지 않게 하기 위해서다.
  - 생성 실패와 버림을 함께 센다. 0으로 돌리는 것은 생성 성공이 아니라 감지 성공(`markHealthy`)이다. 만들자마자 컨텍스트를 잃는 일이 반복될 때도 간격이 늘어나게 하기 위해서다.

### 2. 감지기 상태 알림과 장기 장애 안내 (F5)

- **상태 (`DetectorHealth`):** `starting`(시작 중), `ok`(정상), `retrying`(재시도 중), `fault`(장애)
  - 장애가 되는 경우는 두 가지다. 기다려도 풀리지 않는 원인(`webgl-unavailable`, `model-invalid`)은 첫 실패부터다. 그 밖의 원인은 연속 3회부터다(가안, `detectorFaultAfterFailures`).
  - 장애여도 재시도는 간격대로 계속한다. 운영자가 원인을 고치면 저절로 돌아오게 하기 위해서다.
  - 장애 중에는 카메라 재연결로 재시도를 앞당기지 않는다. 카메라가 자주 끊길 때 생성이 몰리지 않게 하기 위해서다.
- **경계:** `presence-monitor.js`의 `getDetectorHealth()`·`subscribeDetector()`는 `{ health, cause, since }`만 준다. 좌표·점수는 여전히 D 전용 `getDebugSnapshot()`으로만 꺼낸다.
- **안내 규칙 통합 (`guidance.js`, 순수 함수):**
  - 카메라·감지기 중 하나라도 쓸 수 없으면 "준비 중"이다.
  - 30초 이상 이어지거나 스스로 풀리기 어려운 상태면 "직원 문의"다. 카메라는 `unsupported`·`permission-denied`, 감지기는 `fault`가 여기에 해당한다.
  - 시간은 둘 중 하나라도 쓸 수 없게 된 때부터 이어서 잰다. 예를 들어 카메라 단절 20초 뒤 감지기 재생성 대기로 넘어가도 처음부터 다시 재지 않는다.
  - 기존 카메라 문구 규칙(1단계 확정)을 그대로 넓힌 것이고, 문구는 바꾸지 않았다.
- **화면:**
  - 감지기를 쓸 수 없으면 "인식됨/인식 안됨" 표시를 숨긴다. 장애가 "사람 없음"처럼 보이지 않게 하기 위해서다.
  - 쿨타임 문구는 안내 문구가 없을 때만 보인다.
  - 회차 진행 중(카운트다운·촬영·결과)에는 안내 문구를 숨긴다. 3-3까지는 결과 중에만 숨겼다. 카메라가 끊기면 카운트다운은 바로 취소되므로, 여기서 새로 숨는 것은 감지기 장애 중 `S` 수동 촬영의 안내뿐이다.
- **`S` 수동 촬영:** 상태 기계는 카메라 준비만 보므로 감지기 장애와 무관하다. 코드 변경 없이 브라우저에서 확인했다.
- **D 화면:**
  - `detector` 줄: 루프 상태, health, 원인 코드와 한국어 설명
  - 정상이 아닐 때 더하는 줄: `failure`(실패 메시지), `retry`(연속 실패, 시도 수, 다음 재시도까지 남은 시간, 쓸 수 없던 시간)
  - 그 밖의 줄: `webgl`(버전·렌더러·`(software)`), `model`(`sha256 ok`), `guidance`

### 3. WebGL·하드웨어 가속 점검 (웹 쪽)

- 사전 확인에서 WebGL이 없으면 `webgl-unavailable`("하드웨어 가속 꺼짐 또는 WebGL 없음")로 바로 장애가 된다. 관람객 화면은 "직원 문의", D 화면은 원인을 보인다.
- **실행 중 컨텍스트 손실:** 넘긴 캔버스의 `webglcontextlost`를 받아 바로 버리고 `webgl-context-lost`로 표시한다. 이전에는 감지가 15회 실패할 때까지 기다렸다. 이후 처리는 감지 실패 버림과 같은 경로(재시도 중 → 간격 뒤 재생성)다.
- **소프트웨어 렌더러:** 장애로 보지 않는다. 실제로 감지가 동작했기 때문이다. D 화면에만 `(software)`로 표시한다.
- **Chrome 155 관찰:**
  - `--disable-gpu`만 주면 WebGL은 소프트웨어(`Microsoft Basic Render Driver`)로 남고 감지도 동작했다.
  - `--disable-webgl`(+`--disable-webgl2`, `--disable-3d-apis`)은 `<canvas>` 요소의 WebGL만 끄고, MediaPipe가 쓰는 `OffscreenCanvas`는 끄지 못했다.
  - WebGL이 완전히 없어진 경우는 `--disable-gpu --disable-software-rasterizer`와 `--use-gl=disabled`였다.
  - 현장 Chrome 설정 "하드웨어 가속 사용" 끄기가 이 중 어느 경우와 같은지는 확인하지 않았다(**미검증**).

### 4. 반복 오류 로그 제한

- 새 모듈 `log-limit.js`를 만들었다. 공용 인스턴스는 `errorLog`다.
- 분류별로 처음 한 번 남기고, 같은 오류가 이어지면 60초(가안)마다 "같은 오류 N회 더 (마지막 시각)"를 남긴다. 회복하면 감춰진 횟수를 요약하고 기억을 지운다. 숫자만 다른 오류(경과 ms)는 같은 오류로 센다.
- 적용 대상:
  - 카메라 연결 실패. `ready`가 되면 지운다.
  - 감지기 생성 실패·버림. 생성에 성공하면 지운다.
  - 감지 실패. 감지에 성공하면 지운다. 이전 규칙(첫 번째와 15번째)은 이것으로 바꿨다.
  - 촬영 실패. 결과가 나오면 지운다.
  - 사진 정리 실패, 감지기 닫기 실패
- 별도 타이머는 두지 않았다. 요약은 다음 오류나 회복 때 남는다.
- 브라우저가 직접 찍는 네트워크 404·CSP 메시지는 제한할 수 없다.

| 모델 404 | 흉내: CDP `Fetch`로 모델 요청에 404 응답 (파일은 그대로) | 2 → 10 / 3 → 11 | 0 → 0 / 1 → 1 | 15 → 1 |
| 손상 모델 | 흉내: CDP `Fetch`로 같은 크기의 잘못된 바이트 응답 | 2 → 8 / 3 → 11 | 0 → 0 / 1 → 1 | 15 → 1 |
| WebGL 없음 | 실제 Chrome 플래그 `--disable-gpu --disable-software-rasterizer` | 2 → 3 / 3 → 9 | 0 → 0 / 1 → 1 | 56 → 1 |
| MediaPipe 생성 실패 5회 연속 (사전 확인 통과 뒤) | 흉내: 페이지에서 `createFaceDetector`를 직접 불러, 모델 대신 LICENSE 파일과 그 크기·SHA-256을 넘김 → 그래프 시작에서 실패 | 1 → 11 / 2 → 12 | 1 → 1 / 1 → 1 (확인용 WebGL 컨텍스트 5개는 모두 놓음, 살아 있는 컨텍스트 1개 유지) | — |

- `<script>`는 수정 후 `main.js` 1개뿐이다. 정상 생성 뒤에도 로더 요소가 남지 않는다.
- 60초 타이머는 정상 감지기가 있으면 1개(그 감지기의 통계 로거)다.
- 모델 404는 처음 측정(작업 중)과 커밋 뒤 다시 잰 값이 같았다.
- JS 힙(`Runtime.getHeapUsage`)은 수정 후 1.0~1.1MB로 일정했다. **wasm 메모리는 JS 힙에 들어가지 않아 재지 못했다(미검증).** 다만 사전 확인에서 막히는 경우는 wasm 인스턴스를 만들지 않는다.
- **수정 전 안내의 문제:** 수정 전 404 경우는 카메라가 준비된 뒤 관람객 화면에 아무 안내가 없었다. 감지기가 없는데도 "인식 안됨"만 보였다(F5 증상).

**장애 안내와 D 화면 (수정 후)**

| 경우 | 결과 |
|---|---|
| 모델 404 | 처음 `retrying / model-unavailable`, 안내 "준비 중". 약 30초 뒤 "직원에게 문의해 주세요". 3번째 실패(45초 부근)에 `fault`. D `retry` 줄에 다음 재시도까지 남은 시간 |
| 손상 모델 | 0.5초에 `fault / model-invalid (모델 파일 손상 (크기·SHA-256 불일치))`, 바로 "직원 문의" |
| WebGL 없음 (실제 플래그) | 0.4~1.5초에 `fault / webgl-unavailable (하드웨어 가속 꺼짐 또는 WebGL 없음)`, 바로 "직원 문의", `failure : WebGL is not available ...`, 다음 재시도 15초 → 30초 |
| WebGL 없음 + `S` | 카운트다운 동안 안내 숨김 → 결과 1080×1920 표시 → 대기로 돌아와 `completed 1`, `object URLs 0, canvases 0`, 안내 다시 보임 |
| 소프트웨어 WebGL (`--disable-gpu`만) | 감지 정상(`running`, 인식됨), D `webgl : webgl2 ANGLE (Microsoft, Microsoft Basic Render Driver ...) (software)`, 안내 없음. 이 상태의 감지 시간은 기록하지 않았다(**미측정**) |
| 실행 중 컨텍스트 손실 | 흉내: 하네스가 살아 있는 WebGL 컨텍스트에 `WEBGL_lose_context.loseContext()`. 즉시 `retrying / webgl-context-lost`, 안내 "준비 중", 인식 표시 숨김. 이 사이 `S` → 결과 → `completed 1`. 15.2초 뒤 재생성 → `running, health ok`, 안내 없음, 자원 0 |

**정상 사이클 (수정 후)**

- **`S` 수동:** 3초 뒤 결과 → 쿨타임 → 대기, `completed 1`, `object URLs 0, canvases 0, pending jobs 0`. 커밋 뒤 다시 확인했다.
- **자동 시작:** 작업 중 세 번의 실행에서 실제 OBS 영상에 사람이 있어 `round 1 by presence` → 결과 → `completed 1` → `round 2 by presence`를 봤다. 이 실행들의 앱 코드는 커밋된 것과 같고, 이후에는 테스트만 바꿨다.
  - 커밋 뒤 다시 잰 두 번의 실행에서는 카메라 앞에 사람이 없어 자동 시작을 다시 보지 못했다.
  - 한 실행에서는 자동 회차가 완료 없이 다음 자동 회차로 넘어갔다. 새 회차 시작 때 `lastEnd`를 비우는 기존 동작 때문에 D에 이유가 남지 않았다. 사람이 움직여 이탈 취소된 것으로 보이지만 확인하지 못했다.
- 외부 요청 0건, 페이지 예외 0건이었다. CSP 통계 차단 메시지는 감지기를 닫을 때 기존과 같이 나온다.

| 항목 | 기대 동작 |

## 남은 문제

- **라이브러리 의존 우회:** 통계 타이머 정리는 MediaPipe 1.1.1 내부 동작(60000ms)에 기댄다. 버전을 올리면 번들을 다시 읽고 이 측정을 다시 해야 한다.
- **실패한 wasm 인스턴스:** 사전 확인을 통과한 뒤 생성이 실패하면(원인 불명) wasm 인스턴스를 GC에 맡긴다. 참조는 남기지 않지만 메모리는 재지 못했다. 이 경우에도 재시도 간격이 최대 300초라 하루 최대 약 290회다.
- **일시적인 WebGL 없음:** GPU 프로세스 재시작 같은 이유로 WebGL이 잠깐 없을 때도 `webgl-unavailable`은 첫 실패부터 장애다. 그래서 다음 재시도(15초)까지 "직원 문의"가 보일 수 있다.
- **가안 값:** 재시도 상한 300초, 장애 기준 연속 3회, 로그 요약 60초
- **브라우저 하네스:** 이번에도 저장소 밖 임시 하네스를 썼다. 저장소 안 하네스는 4-4다.
- 3-3에서 넘긴 `toBlob` 무응답(`capture busy`) 상태는 촬영 실패 로그 제한만 적용됐다. 운영자 알림은 따로 만들지 않았다.
