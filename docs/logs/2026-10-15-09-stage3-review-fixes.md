## 수정 내용과 결정

### A. 캡처 예외 정리와 실패 뒤 자동 시작 대기

- **정리:** `grabFrame()`은 캔버스를 만든 직후부터 크기 지정·`getContext`(null이면 예외)·`drawImage` 중 어디서 실패해도 그 캔버스를 비우고 예외를 다시 던진다.
- **실패 뒤 대기:** 상태 기계(`session.js`)가 연속 실패 수와 자동 시작을 다시 허용할 시각(`retryAt`)을 기록한다.
  - 대기는 `failureRetryMs` 5초부터 실패마다 두 배, 최대 `failureRetryMaxMs` 60초다(가안, `config.session`).
  - 대기가 끝나면 상태 기계가 알리고, 자동 시작이 다시 평가한다.
  - 성공하면 기록을 지운다.
  - `auto-start.js`의 레벨 판정은 대기 중이면 `blocked: capture-failed (retry wait)`를 돌려준다.
- **정상 연속 촬영과 분리:** 쿨타임 뒤 바로 다음 회차를 시작하는 정책은 그대로 둔다. 실패 대기는 실패한 경우에만 붙는다.
- **`S`는 막지 않는다.** 운영자가 원인을 고친 뒤 바로 시험할 수 있게 하기 위해서다. `X`는 실패 기록을 지우지 않는다. 장치 문제가 그대로인데 초기화만으로 빠른 반복이 다시 시작되지 않게 하기 위해서다.
- **기록 위치:** 상태 기계는 타이머를 주입받고 있어 대기 만료를 테스트하기 쉽다. 정책(자동 시작만 쉰다)은 `auto-start.js`의 판정에 두었다.
- **D 화면:** `failures` 줄(연속 실패 수, 자동 시작까지 남은 시간), `last end` 줄(실패 이유), `resources` 줄(`pending jobs`)

### B. 회차별 취소 경계

- 상태 기계는 촬영마다 `AbortController`를 새로 만들어 `takePhoto({ signal })`로 넘긴다. 제한 시간 초과와 강제 초기화로 대기로 갈 때 abort한다(`goIdle` 한 곳). 정상으로 끝난 회차의 신호는 abort하지 않는다.
- `capture.js`:
  - 효과·인코딩을 `untilAborted()`로 기다린다. abort되면 기다리지 않고 바로 실패하고, `finally`에서 캔버스를 비운다. `toBlob`은 호출할 때 픽셀을 복사하므로 인코딩 중에 비워도 된다.
  - 늦게 도착한 인코딩 결과로는 Object URL을 만들지 않는다.
  - 효과가 신호를 무시하고 나중에 새 캔버스를 돌려주면 그 캔버스도 비운다.
- 효과 경계를 `applyPhotoEffect(canvas, { signal })`로 바꿨다. 효과를 붙일 때 같은 신호를 쓴다.
- **쌓이지 않게:** 끝나지 않은 효과·인코딩 작업 수(`pending`)를 센다. 하나라도 남아 있으면 다음 `take()`는 캔버스를 만들지 않고 `capture busy`로 바로 실패한다. 브라우저 `toBlob`은 취소할 수 없으므로, 콜백이 끝내 오지 않는 이상 상태에서는 촬영이 계속 실패하고 A의 대기가 붙는다. 상한을 하나로 둔 이유는 정상이라면 다음 촬영(최소 3초 뒤) 전에 인코딩(수십 ms)이 끝나기 때문이다.

### C. 촬영 직전 새 프레임 확인

- `camera-monitor.js`에 `getFrameInfo()`를 더했다. 실제 새 프레임을 받은 마지막 시각(`performance.now()`)과 누적 수(세대)를 돌려준다. 모든 `requestVideoFrameCallback` 콜백에서 갱신한다.
  - 끊김 판정용 `lastFrameAt`과 따로 둔 이유: `lastFrameAt`은 페이지가 숨겨진 동안 현재 시각으로 밀어 두어 실제 프레임 시각이 아니다.
- **캡처:** `take()`가 캔버스를 만들기 전에 마지막 새 프레임이 `config.capture.maxFrameAgeMs`보다 오래됐으면 `stale frame`으로 실패한다. 실패하면 A의 대기가 붙는다.
  - 값은 500ms(가안)다. 30fps 프레임 간격(약 33ms)보다 충분히 길고, 끊김 판정(3초)보다 짧다.
- **인식:** `presence-monitor.js`는 감지할 때마다 누적 프레임 수를 보고, 직전 감지 이후 새 프레임이 없으면 감지를 건너뛴다. 인식 상태는 그대로 두고, 끊김 판정은 카메라 감시가 맡는다.
  - 좌표·점수는 여전히 밖으로 나가지 않는다. 카메라가 내보내는 것도 시각과 수뿐이다.
  - D `faces` 줄에 `same-frame skips` 수를 보인다.

### D. 판정 기준이 바뀌면 인식 상태를 다시 잰다

- `presence-monitor.js`의 `setSettings()`는 기준(영역·얼굴 크기·신뢰도·두 시간)이 하나라도 바뀌면 인식 상태를 처음 상태로 돌리고 바로 "인식 안됨"을 알린다. 비교는 새 순수 함수 `presence.js`의 `sameCriteria()`로 한다.
  - 바뀌는 경우는 조절 중 변경, 취소·닫기 복원, 기본값으로 되돌리기를 모두 포함한다.
  - 값이 같으면 다시 재지 않는다.
- 저장 없이 닫는 순서는 다음과 같다. 그래서 닫는 순간에는 인식 안됨이라 시작하지 않고, 새 기준으로 `presentHoldMs`(0.5초) 동안 다시 확인된 뒤에만 시작한다.
  1. 저장값 복원(`setSettings`)
  2. "인식 안됨" 알림
  3. `evaluate('tuning-closed')`
- **영향:** 조절하는 동안 인식 표시가 잠깐 "인식 안됨"이 됐다가 돌아온다. 인식으로 시작한 카운트다운 중에 기준을 바꾸면 그 회차는 취소된다. 새 기준을 확인하지 않은 채 찍는 것보다 낫다고 봤다.
- D `faces` 줄에 `criteria resets` 수를 보인다.

### E. 테스트 보강

- 공용 흉내를 `tests/helpers.mjs`로 모았다.
  - 가짜 시계·타이머, 인식 상태, 캔버스·Object URL

| D 통합 (감지 루프 + auto-start + 상태 기계) | 임시 기준으로 인식됨 → 저장 없이 닫아 얼굴이 영역 밖인 기준으로 복원 → 시작 안 함(3초, 회차 0). 복원 기준으로도 인정되면 닫는 순간 시작 안 함 → 0.45초 대기 → 0.65초 시작(계기 `presence: present`) |
| E | 늦은 타이머: 1300ms에 숫자 2, 다음 예약 2000ms. 2200ms에 숫자 1, 다음 예약 3000ms. 2999ms까지 촬영 0, 3000ms에 촬영 |

## 남은 문제

- 자동 시작과 D는 이번 수정 뒤 브라우저에서 사람으로 확인하지 못했다. Node 통합 테스트로만 확인했다.
- 실패 대기 값(5초부터 두 배, 최대 60초)과 `maxFrameAgeMs` 500ms는 가안이다. 현장 카메라 fps가 아주 낮으면(예: 2fps 미만) 500ms가 짧을 수 있다.
- 브라우저 `toBlob`은 취소할 수 없다. 콜백이 끝내 오지 않으면 그 뒤 촬영은 계속 `capture busy`로 실패한다. 이 상태를 운영자에게 알리는 방법은 F5와 함께 4단계에서 다룬다.
- 4단계로 넘긴 항목은 위 "함께 4단계로 넘긴 권고"와 `docs/PROJECT.md` 4절에 있다. 그중 F4(MediaPipe 생성 실패 누적)는 무인 운영 전에 해결해야 한다.
