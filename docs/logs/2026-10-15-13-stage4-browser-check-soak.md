## 결정과 이유

- **의존성 없음:** Node 24 내장 `WebSocket`으로 CDP에 직접 붙는다. 4-1~4-3에서 쓴 임시 하네스와 같은 방식이다.
- **포트 충돌 없음:**
  - 서버는 운영체제가 고른 빈 포트로 띄운다.
  - Chrome은 `--remote-debugging-port=0`으로 띄우고, 실제 포트는 임시 프로필의 `DevToolsActivePort` 파일에서 읽는다.
  - 현장 서버(8765)나 다른 Chrome과 겹치지 않는다.
  - `--user-data-dir`를 늘 주므로 사용자의 Chrome에 붙지 않는다(메모리 지침: 사용자 Chrome에 붙는 실행 금지).
- **앱 상태는 D 화면 글자로 읽는다. 앱 코드에 확인 전용 훅을 넣지 않았다.**
  - D 화면에 필요한 값(카메라·감지기·상태 기계·사진 자원·안내·감지 빈도·설정 출처)이 이미 모두 있다.
  - 대가는 D 줄 형식에 묶인다는 점이다. 형식을 바꾸면 도구도 고쳐야 한다(`docs/SYSTEM.md`에 적음).
- **카메라 권한은 CDP `Browser.setPermission`으로 준다.**
  - 처음에는 이전 하네스처럼 `--use-fake-ui-for-media-stream`을 썼다. 그런데 이 플래그는 CDP로 "거절"한 권한까지 자동 수락해서, 권한 거절 시나리오가 15초 동안 `ready`인 채로 실패했다.
  - 플래그를 빼고, 열기 전에 `granted`를 설정하는 방식으로 바꿨다.
- **조절값 API 시나리오는 실제 저장 파일을 잠깐 바꾼다.**
  - 서버는 저장 파일 경로가 하나로 고정돼 있다(4-3 설계). 그래서 시험용 경로를 따로 둘 수 없다.
  - 실행 전 바이트를 읽어 두고, 끝나면 같은 바이트로 되돌린다(서버 원자적 쓰기, 바이트 대조). 없던 파일이면 지운다.
  - 현장 키오스크가 같은 저장소에서 도는 PC에서는 실행하지 말라고 README·SYSTEM에 적었다.
- **CSP:** MediaPipe 사용 통계 전송(`odml.pa.googleapis.com`)의 CSP 차단은 의도된 동작이다(1절). 따로 세고 실패로 보지 않는다. 그 밖의 CSP 위반은 실패다.
- **자동 시작은 범위 밖이다.** Chrome 가짜 카메라 영상에는 얼굴이 없다. 자동 시작·이탈 취소·인식 중 `P`는 Node 통합 테스트와 사람의 실측으로 확인한다.
- **장시간 실측은 같은 도구의 `--soak` 모드로 했다.** 서버·Chrome·정리 코드를 함께 쓰기 위해서다.
  - 원자료 CSV의 기본 위치는 `logs/`이고, 이미 Git에서 제외돼 있다.
  - 이번 실측의 CSV는 `%TEMP%`에 두었다가 요약 뒤 지웠다.
  - **기본 실측 시간은 10분이다(사용자 요청).** `--soak`만 주면 10분이고, 더 길게 돌릴 때만 `--soak 60`처럼 분을 준다.

**해석**

- 리스너·문서 수는 1분 이후 평평했다. DOM 노드는 465~478 사이를 오갔다(결과 화면·D 화면 갱신).
- JS 힙은 강제 GC 없이 읽은 값(`Performance.getMetrics`)이라 4.4~5.5MB 사이를 오르내렸다.
- Chrome 메모리는 시작 직후(감지기 생성) 높았다가 1분에 내려간 뒤 9분 동안 +21MB(662.7 → 683.8)였다.

- 기록 시점이 `S`를 누른 직후(카운트다운)라, 그 순간의 사진 자원 0은 당연한 값이다. 정리 확인은 `taken = released`로 본다. 다음에 고칠 점: 기록 시점을 `S` 간격과 엇갈리게 두면 결과·쿨타임 중 값도 볼 수 있다.

## 사용자 실측 체크리스트 (자동화할 수 없는 것)

현장 PC에서 `Launch.bat`으로 띄운 키오스크 기준이다. 키오스크 화면에서 운영자 키를 쓰려면 키보드·마우스를 연결한다. `D`를 켜 두면 상태를 읽기 쉽다(관람객 앞에서는 끈다).

**준비**

1. OBS 가상카메라가 켜진 상태에서 `Launch.bat` → 키오스크가 뜨고 미리보기가 보인다.
2. `D` → `status : ready`, `detector : running, health ok`, `webgl` 줄에 GPU 이름(`(software)`가 아님)이 보인다.
3. `R`로 인식 범위를 조절하고 "저장" → `D` `settings : saved`. 저장소에 `config\presence.local.json`이 생긴다.

**매트에 실제로 서고 떠나기**

4. 매트에 선다 → 약 0.5초 뒤 "인식됨" → 3·2·1 → 결과 10초 → 쿨타임 5초. 계속 서 있으면 다음 회차가 바로 시작된다.
5. 카운트다운 중 매트를 떠난다 → 약 1초 뒤 취소, 쿨타임 없이 대기. 다시 서면 새로 시작한다.
6. 여러 명(가족)이 서거나, 아이 키·고개 돌림처럼 얼굴이 작거나 옆을 볼 때 인식되는지 본다. 잘 안 되면 `R`로 최소 얼굴 크기·신뢰도를 조정한다.
7. 카운트다운 중 `P` → 바로 취소되고 오른쪽 위에 "자동 촬영 일시정지 (P)"가 보인다. 서 있어도 시작하지 않는다. 다시 `P` → 곧 시작한다.

**OBS 중지**

8. 대기 중 OBS에서 가상카메라 중지 → 약 3초 안에 화면이 검게 바뀌고 "준비 중입니다. 잠시만 기다려 주세요." 30초가 지나면 "직원에게 문의해 주세요."
9. 가상카메라 다시 시작 → 자동으로 다시 연결되어 미리보기와 인식이 돌아온다(약 3초 간격으로 재시도).
10. 카운트다운 중 가상카메라 중지 → 촬영하지 않고 취소된다. 다시 켜면 회복된다. 사람이 서 있어도 자동 시작은 실패 대기(5초~) 뒤다.

**절전 후 복귀**

11. Windows 절전(또는 모니터 끄기) → 복귀 → 미리보기·감지가 돌아오는지 본다. `D` `detector`가 `retrying`이면 15초 안에 `ok`가 되는지 본다. "직원 문의"가 계속 남으면 기록한다.

**4K 출력**

12. OBS 출력 해상도를 2160×3840으로 바꾸고 가상카메라를 다시 시작 → `D` `video : 2160x3840`
13. `S` → 결과가 2160×3840으로 나오는지(`D` `capture` 줄), 인코딩 시간(`encode ...ms`), 카운트다운 숫자가 끊기지 않는지 본다. `detect` 줄 빈도가 15fps 근처인지 본다.

**키오스크 화면**

14. 경고 막대·번역 제안·복원 말풍선이 보이지 않는다. 화면 핀치·스와이프로 페이지가 바뀌지 않는다.
15. `Shutdown.bat` → 키오스크와 서버만 닫히고 일반 Chrome·OBS는 남는다. `Launch.bat` → 같은 조절값으로 다시 뜬다.

**장시간**

16. 행사 시간만큼(가능하면 하루) 켜 둔다. 끝날 때 `D` `resources : object URLs 0, canvases 0, pending jobs 0`(대기 중)인지, 작업 관리자에서 Chrome 메모리가 처음보다 크게 늘지 않았는지 본다.

기록할 것: 어긋난 항목 번호와 그때 `D` 화면의 `status`·`detector`·`session`·`last end` 줄

## 남은 문제

- 확인 도구는 D 화면 줄 형식에 기댄다. D 형식을 바꾸면 함께 고쳐야 한다.
- 자동 시작·이탈·여러 명·실제 키오스크·OBS 중지·절전·4K는 도구 범위 밖이다. 위 체크리스트로 사람이 확인한다.
- 조절값 API 시나리오는 실제 저장 파일을 몇 초 동안 바꾼다(되돌림). 현장 PC에서는 도구를 돌리지 않는다.
- 장시간 실측은 개발 PC(고성능 GPU)에서 **10분**이었다. 누수 여부를 판단하기에는 짧다. 더 긴 실측(`--soak 60` 이상), 현장 PC, 하루 단위 운영은 체크리스트 16번으로 확인한다.
- 실측 기록 시점이 `S` 간격(20초)과 맞물려 늘 카운트다운 중에 기록됐다. 결과·쿨타임 중 값을 보려면 기록 시점을 엇갈리게 둔다(후속 개선 후보).
